# MX OEM STOCK 单车 POC 首次执行排查与修订结论

> [!warning] 当前参数已被替代
> 本页记录的是 2026-07-18 单车 POC 当时使用 `220202` 成功的历史事实。用户于 2026-07-22 确认 UAT 当前已改用 `270165`；现行批量执行参数见 [[05 UAT客户号切换为270165决策]]，不得继续从本页复制 `220202`。

## 本次执行结论

单车 UAT POC 已完成采购发运导入、Gate In 和成功入库。此前两次失败来自 Excel 转 JSON 参数语义混用，不是外层 JSON 数组格式错误；修正为总部卖方 `5000` 和 UAT 墨西哥买方 `220202` 后，单车链路通过。

## 已验证事实

### 组织编码与业务角色

- 用户提供的主数据查询截图显示，总部组织使用销售公司编号 `5000`。
- 生产墨西哥记录显示客户编号 `270165`、销售公司编号 `L000`。
- UAT 墨西哥记录显示客户编号 `220202`、销售公司编号 `E000`。
- `/ops/smpOrder/save` 的采购订单顶层 `salesCompanyNo` 表示卖方销售公司，不表示买方所属的墨西哥销售公司。
- `LmGDSDeliveryService.validateSalesCompany()` 明确要求发运关联采购订单的卖方销售公司为 `5000`；传 `E000` 会触发 `lm.delivery.order.notPurOrder`。

因此本次 POC 当时使用的角色组合是：卖方 `salesCompanyNo=5000`，生产买方 `customerNo=270165`，UAT 买方 `customerNo=220202`。生产 `L000/270165` 与当时 UAT `E000/220202` 的映射只在本次 POC 范围得到验证；该映射已被 [[05 UAT客户号切换为270165决策]] 替代，不再作为当前执行参数。

### Excel 与 JSON 字段来源

| JSON 字段 | 来源 | 本次 UAT 目标值 |
|---|---|---|
| `customerNo` | 订单 Sheet 的 `DEALER SAP NO` | `220202` |
| `deliveryItemVos[].customerNumber` | 发运 Sheet 的 `客户编号` | `220202` |
| `deliveryItemVos[].shipToPartyNumber` | 发运 Sheet 的 `送达方编号` | 待核对 UAT 仓库主数据 |
| `salesCompanyNo` | 调用 `/ops/smza-order/initGdsShippingData` 时的请求参数 | `5000` |

`salesCompanyNo` 不从 Excel 读取。生成 JSON 中曾出现组织 UUID，是因为转 JSON 接口的同名请求参数传入了组织 UUID，代码随后原样写入 `OrderVo.salesCompanyNo`。

### 两次失败的原因

1. 传组织 UUID 作为 `salesCompanyNo` 时，`DataInitializationService` 按销售公司编号查询组织，返回 `masterdata.organization.SalesCompanyNoNotExist`。
2. 改传 `E000` 后，订单进入发运保存阶段，但 `LmGDSDeliveryService.validateSalesCompany()` 要求采购自总部 `5000`，返回 `lm.delivery.order.notPurOrder`。

接口响应外层 `success=true` 只表示批处理请求完成；实际逐单结果必须检查 `data.successList`、`data.duplicateIgnored` 和 `data.failed`。本次两个响应的 `successList` 均为空，因此不能标记为导入成功。

### JSON 数组错误日志

`/ops/smpOrder/save` 的 Controller 参数是 `List<OrderVo>`，请求体外层数组正确。`ParameterRequestWrapper` 先按 `JSONObject` 解析数组会记录 `can not cast to JSONObject`，但异常被捕获后会把原始 JSON 放回请求流；该日志不是本次逐单失败原因。

## 原 SQL 修订结论

[[../99 历史草案/01 单车生产只读SQL旧稿]] 已标记为 `deprecated`，由 [[02 批量生产只读取数]] 替代：

- 第 1 段的 `sales_company_no=5000` 与生产 `customer_no=270165` 分别代表总部卖方与墨西哥买方；单车成功后不再将其认定为冲突。
- 第 1 段的 `latest_gds_missing_count` 检查了 `g.id`，却遗漏了第 5 段和转换代码必需的 `g.etd`，因此候选计数为 0 也不能证明日期齐全。
- 第 3、4 段导出的生产客户编号不能直接作为 UAT 主数据使用；订单 Sheet 的 `DEALER SAP NO` 和发运 Sheet 的 `客户编号` 需要按 UAT 已核验值回填。

## 单车验收结果

- 用户确认单车使用卖方 `5000`、UAT 买方 `220202` 完成采购发运导入。
- 用户确认同一单车已完成 Gate In 并成功入库。
- 这证明当前单车数据使用的送达方、目的港和仓库组合在 UAT 能通过，但不自动证明其余车辆的仓库映射全部正确。
- 单车 POC 验收通过；批量 UAT 和生产就绪仍未验证。
