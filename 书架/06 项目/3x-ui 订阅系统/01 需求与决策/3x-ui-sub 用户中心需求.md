# 3x-ui-sub 用户中心需求

## 1. 背景

目前3x-ui自定义订阅主题可以展示用户流量、有效期和订阅地址，但不具备可靠的账号登录、套餐管理、权限控制和操作审计能力。需要在现有 `3x-ui-sub` 项目中新增独立Portal，逐步承接用户自助服务。

## 2. 产品目标

建设一个轻量、安全的用户中心，使用户能够：

- 使用账号登录；
- 查看账号状态、套餐、流量与到期时间；
- 获取、复制和重置自己的订阅地址；
- 查看客户端导入说明；
- 在不接触3x-ui面板的情况下完成常用自助操作。

## 3. 非目标（第一阶段）

- 不开发在线支付和自动结算；
- 不开放公众自助注册；
- 不替代3x-ui的入站、节点和Xray管理；
- 不让浏览器直接调用3x-ui管理API；
- 不让客户端订阅依赖Portal登录Cookie；
- 不直接修改3x-ui数据库。

## 4. 系统边界

```text
用户浏览器
  → Nginx HTTPS
  → Portal（登录、页面、业务权限）
       ├→ PostgreSQL（账号、套餐、映射、审计）
       ├→ 3x-ui API（客户端、流量、到期时间）
       └→ Gateway（创建/轮换订阅token）

Clash/Mihomo
  → Nginx HTTPS
  → Gateway（token鉴权与配置生成）
  → 3x-ui原生订阅
```

建议公开路径：

```text
https://sub.example.com/                 Portal
https://sub.example.com/clash/<token>    Mihomo订阅接口
https://sub.example.com/sub/<token>      通用订阅接口（可选）
```

## 5. 角色

### 普通用户

- 登录自己的账户；
- 只查看自己的套餐和流量；
- 复制或重置自己的订阅；
- 查看公告和客户端教程。

### 管理员

- 创建、停用和恢复用户；
- 绑定用户与一个或多个3x-ui客户端；
- 分配流量、到期时间和套餐；
- 重置订阅token；
- 查看关键操作审计记录。

## 6. MVP功能需求

### 6.1 身份认证

- 管理员邀请或创建账号；
- 用户名/邮箱加密码登录；
- 密码使用Argon2id或bcrypt哈希存储；
- 使用 `HttpOnly`、`Secure`、`SameSite` Cookie维护会话；
- 登录失败限速和短时锁定；
- 支持退出登录和管理员强制失效会话；
- 首次登录要求修改初始密码。

### 6.2 用户首页

复用现有主题的视觉结构，展示：

- 服务状态；
- 已用、剩余和总流量；
- 到期时间或永久有效；
- 最近在线时间；
- 可用线路数量；
- 公告与支持链接。

### 6.3 订阅管理

- 展示脱敏后的个人订阅信息；
- 一键复制Mihomo订阅地址；
- 提供Clash Party、Clash Verge Rev和手动导入说明；
- 用户确认后重置订阅token；
- 重置后旧token立即或在短宽限期后失效；
- 明确提示订阅地址等同密码，不可公开。

### 6.4 3x-ui集成

- Portal后端登录或认证3x-ui管理接口；
- 查询指定客户端的启用状态、流量、到期时间和最近在线；
- 管理员可创建、停用、恢复和修改客户端限额；
- 通过本地映射表关联 `portal_user_id`、3x-ui实例和客户端标识；
- API不可用时显示“数据暂不可用”，不得误报余额为零；
- 对API调用设置超时、有限重试和熔断。

### 6.5 管理端

- 用户列表与搜索；
- 创建、禁用和恢复用户；
- 设置套餐、流量上限和到期时间；
- 绑定/解绑3x-ui客户端；
- 重置订阅和会话；
- 查看最近的安全与管理操作。

## 7. 数据模型（初稿）

- `users`：账号、密码哈希、状态、角色、创建时间。
- `sessions`：会话摘要、过期时间、撤销状态、登录信息。
- `plans`：套餐名称、流量、有效期和说明。
- `user_plans`：用户套餐实例、开始/结束时间、状态。
- `xui_instances`：3x-ui实例地址、加密后的服务凭据、状态。
- `xui_client_bindings`：用户、实例、入站和客户端标识映射。
- `subscription_tokens`：token哈希、用户、状态、创建与撤销时间。
- `audit_logs`：操作者、动作、目标、结果、时间和必要上下文。

数据库不保存明文订阅token；仅保存安全哈希，明文只在创建/轮换时返回。

## 8. 安全要求

- 3x-ui管理API不暴露给公网浏览器；
- 服务凭据使用环境变量、系统凭据或加密存储，不写入仓库；
- 所有公开入口强制HTTPS；
- 对登录、token重置和订阅下载分别限速；
- Nginx访问日志不得记录完整订阅token；
- 管理操作需要CSRF防护和二次确认；
- 普通用户所有查询必须按当前会话用户过滤；
- 订阅接口保留token机制，不能改为Cookie鉴权；
- 定期轮换管理凭据并备份PostgreSQL。

## 9. 技术建议

- 后端继续使用Go，与现有Gateway技术栈一致；
- Portal和Gateway可同仓库分模块，但保持独立职责；
- 复用现有PostgreSQL，不与3x-ui表混用schema；
- 前端优先服务端渲染或轻量HTML模板，降低1GB服务器负担；
- 初期以systemd部署，不强制引入Docker；
- 对Portal和Gateway分别设置内存、CPU及文件句柄限制。

## 10. 迁移方案

### 阶段一：并行

- 保留现有3x-ui订阅主题和旧用户入口；
- 部署Portal，仅邀请测试账号；
- Portal读取3x-ui数据但不自动修改套餐。

### 阶段二：接管

- 新用户只通过Portal交付订阅；
- 支持token重置和管理员维护套餐；
- 逐步通知旧用户迁移。

### 阶段三：收口

- 清空3x-ui自定义订阅主题或恢复默认；
- 限制原生订阅入口仅供Gateway访问；
- 普通用户只接触Portal和个人订阅接口。

## 11. 验收标准

- 用户只能看到自己的数据和订阅；
- 登录会话安全属性符合要求；
- 流量、到期时间与3x-ui数据一致；
- 重置token后旧地址失效，新地址可正常更新；
- Clash Party和Clash Verge Rev均能订阅同一份Mihomo配置；
- 3x-ui API故障不会导致Portal泄露错误或其他用户数据；
- 管理操作可在审计日志中追踪；
- 在当前服务器负载下，Portal与Gateway运行稳定且不明显挤压3x-ui和PostgreSQL。

- [ ] 是否需要支付、订单和优惠码。
- [ ] 一个账号是否允许绑定多个套餐或多台3x-ui实例。
- [ ] token重置是否提供短时间迁移宽限期。
- [ ] 管理端是否与用户端同域名、同程序。
- [ ] 后续是否迁移到备用服务器并独立部署PostgreSQL。
