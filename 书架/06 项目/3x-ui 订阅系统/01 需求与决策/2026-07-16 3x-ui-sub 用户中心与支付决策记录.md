## 2. 已接受的第一版产品范围

### 2.1 支付渠道

- 业务渠道选择：**链动小铺**。
- 第一版只支持一次性支付；续费通过创建新的单次订单完成。
- 第一版不做自动续费、优惠码、钱包余额、充值账户和发票。

> [!warning] 接入验证门槛
> 当前未取得足以确认“链动小铺”开放接口能力的官方技术文档。正式实施支付前必须取得并核验官方或商户后台提供的下单、签名、异步回调、查单、关单、退款和对账说明。若它只提供托管店铺而不提供可靠的服务端 API，则不能按当前自动开通方案直接接入，需要另开支付渠道变更决策。

### 2.2 注册与账号恢复

- 允许公开邮箱注册，并强制完成邮箱验证后才能购买或获取订阅。
- 找回密码使用邮件找回。
- 邮件验证和找回链接必须为单次、短时有效，数据库只保存令牌哈希。

### 2.3 套餐模型

- 套餐同时受固定周期和固定流量限制。
- 第一版一个账号只允许一个当前有效权益。
- 第一版一个账号绑定一个 3x-ui 客户端，且只接入一个 3x-ui 实例。
- 数据模型保留未来扩展为多客户端和多实例的能力，但第一版界面和业务规则不开放。

### 2.4 续费规则

- 未过期权益从当前到期时间顺延。
- 已过期权益从支付确认时间重新起算，不能从历史到期时间继续顺延。
- 每次续费重置套餐周期内流量额度，不累加上期未使用流量。

“已过期从支付时间起算”和“流量重置”是为补齐原清单未覆盖边界而采用的第一版规则；若业务希望累计流量，需要另开决策记录。

### 2.5 退款

- 不提供用户自助退款。
- 退款仅由管理员人工处理，并记录原因、操作者、渠道结果和权益处置审计。
- 人工确认全额退款成功后，相关权益失效、3x-ui 客户端禁用、订阅 token 撤销并主动清理 Gateway 缓存。
- 第一版不做按剩余时间或剩余流量自动计算的部分退款。

### 2.6 支付成功但开通失败

- 支付确认与资源开通使用两个独立状态。
- 支付成功后创建幂等开通任务，自动重试；超过重试上限后转人工处理。
- 第一版不因单次开通失败自动退款，避免外部系统短暂故障造成错误退款。
- 用户中心应显示“已支付，开通处理中”或“需要人工处理”，不得伪装为未支付或已开通。

## 3. 已接受的技术边界

### 3.1 3x-ui 管理 API 方案

- Portal 通过独立的服务端适配器调用 3x-ui 官方 REST API；以目标面板内置 Swagger 为最终接口依据。
- 浏览器不得直接访问 3x-ui 管理 API，也不得接触管理会话或凭据。
- 第一版适配器只覆盖必要能力：登录/认证、查询入站与客户端、创建客户端、更新流量和到期时间、启用/禁用客户端、查询流量与在线状态。
- 读取请求超时建议 5 秒，可对网络错误执行最多 1 次带退避重试。
- 创建、更新、禁用等写操作不得盲目自动重放；必须使用本地幂等任务、操作前后查询和审计结果控制重试。
- 连续失败时进入短时熔断，并在 Portal 显示“数据暂不可用”。

> [!todo] 实施前验证
> 必须先记录目标 3x-ui 版本，并在隔离测试客户端上验证认证、字段格式、创建、更新、禁用、流量、到期时间和在线状态接口。未完成该验证前，以上仅是 accepted 集成方向，不是 verified API 事实。

### 3.2 订阅 token 失效

- 用户主动重置 token 后，旧 token 立即失效，不提供迁移宽限期；界面必须在操作前二次确认并提示现有客户端需要更新订阅地址。
- 用户禁用、权益到期或退款完成后，token 立即失效。
- Portal 在状态变化时主动通知 Gateway 清理对应缓存。
- Gateway 即使未收到主动通知，也必须通过短时鉴权缓存限制失效窗口；第一版鉴权缓存最长 60 秒，且不得超过权益到期时间。
- 订阅内容缓存与鉴权结果分离；命中内容缓存前仍需确认 token 当前有效。
- 数据库只保存 token 哈希和可展示前缀，不保存明文 token。

### 3.3 旧用户迁移

- 管理员根据现有 3x-ui 客户端映射批量预创建 Portal 账号或迁移记录。
- 使用邮箱邀请用户设置密码并完成账号认领，不要求用户提交完整旧订阅 token。
- 迁移试运行期间旧入口和 Portal 并存，但需设定明确截止日期。
- 用户完成认领后生成新的 Portal 订阅 token；旧 token 按迁移批次撤销。
- 未认领账号在截止日期后进入人工处理，不自动删除 3x-ui 客户端或历史用量。

### 3.4 Portal 与数据库部署

- Portal 与 Gateway 位于同一代码仓库，但作为独立进程运行。
- 管理端与用户端使用同一 Portal 程序、不同路由；管理员路由使用独立角色授权、重新认证和操作审计。
- PostgreSQL 部署在当前主机，但 Portal 使用独立数据库和独立数据库角色，不与 3x-ui 共用数据库或 schema。
- Portal 数据库必须有独立迁移、备份和恢复流程。
- 上线前必须进行内存、磁盘和连接数容量检查；如果当前主机无法稳定承载，数据库部署位置需要重新决策，不能仅因“已选择当前主机”而强行上线。

## 4. 反滥用决策

第一版采用分层反滥用，不默认限制邮箱域名，也不要求邀请码：

- 按 IP 和邮箱对注册、登录、验证码发送、找回密码限速。
- 相同邮箱的验证邮件设置冷却时间和每日上限。
- 只有超过失败或请求阈值时才触发 CAPTCHA，避免所有正常用户都被打扰。
- 登录连续失败后短时锁定账号维度的认证尝试，但不永久锁号。
- 记录脱敏的安全事件，不在日志中保存密码、邮件令牌或完整订阅 token。
- 风险 IP/设备策略延期，等有真实滥用证据后再增加。

## 5. 对账与告警决策

### 必须告警

- 支付已确认但开通任务超过预期时间仍未成功。
- 开通任务超过自动重试上限。
- 3x-ui API 连续失败并触发熔断。
- 支付回调验签失败、订单金额不一致或同一事件出现冲突结果。
- 订单状态、支付状态、权益状态和 3x-ui 客户端状态巡检不一致。

### 必须巡检

- 每日执行订单、支付、权益和开通任务内部一致性巡检。
- 如果链动小铺提供交易查询或对账单 API/导出能力，每日与渠道侧数据对账。
- 如果渠道不提供自动对账能力，第一版保留管理员上传或人工核对流程，并把“缺少自动对账能力”作为上线风险明确记录。

### 通知策略

- 第一版至少支持一种独立于 Portal 页面之外的运维通知渠道。
- 相同故障聚合通知，恢复后发送恢复消息，避免持续重复告警。
- 告警内容不得包含完整订阅 token、支付密钥、3x-ui 凭据或用户密码信息。

## 6. 明确延期或不纳入第一版

- 自动续费。
- 优惠码。
- 钱包余额或充值账户。
- 发票。
- 用户自助退款和自动部分退款。
- 单账号多套餐、多客户端或多 3x-ui 实例。
- 邮箱域名白名单、邀请码注册和常态化 CAPTCHA。
- 独立管理端程序、独立管理域名或 VPN；后续可根据风险再评估。
