# 2026-07-31 3x-ui 私有管理面收口与订阅故障复盘

> [!summary] 阶段结论
> 本轮已将 3x-ui 面板和 SSH 收口到 Tailscale 私网，启用主机默认拒绝入站策略，清理脱离数据库的陈旧 Xray 入站，并恢复订阅转换网关。私有管理链路和公开订阅链路已经分离；公开用户主题页尚未接入 Nginx。

## 环境基线

- 实机输出确认服务器为 Debian 13，3x-ui 版本为 3.6.0。
- 3x-ui 当前生产数据后端为 PostgreSQL。旧 SQLite 文件不是当前生产事实来源。
- 3x-ui、Xray、Nginx、PostgreSQL 和订阅网关运行在同一主机。
- 本记录不保存真实 IP、数据库用户或口令、证书私钥、管理路径、客户端凭据、订阅 ID 或完整订阅地址。

## 已验证的安全收口

### Tailscale 部署过程

本轮在目标 Debian 13 主机上按发行版仓库方式部署 Tailscale：

1. 创建系统 keyring 目录。
2. 安装 Tailscale 官方 Debian trixie 仓库签名 keyring。
3. 添加 Debian trixie 稳定版软件源并刷新 APT 索引。
4. 安装 Tailscale，确认命令可用且 tailscaled 服务为 active。
5. 完成主机登录入网，确认服务器取得 Tailnet 地址。
6. Windows 安装并登录 Tailscale；最初 PowerShell 找不到 tailscale 命令的问题在客户端安装后消失。
7. iOS 安装并登录相同 Tailnet。
8. Windows 的 tailscale status 同时列出 Windows、Debian 和 iOS 三台设备。

安装验收结果：

- Debian 上 tailscale version 返回有效版本信息。
- tailscaled 状态为 active。
- tailscale status 与 tailscale ip 能读取服务器的 Tailnet 身份和地址。
- Windows 可 tailscale ping 到 Debian 主机。
- Windows 与 Debian 曾通过直连路径通信；是否持续直连取决于双方网络环境，DERP 中继仍属于正常可用路径。

本轮没有在 Vault 中保存登录 URL、认证 key、设备私有地址或账户凭据。

### 私网管理接入顺序

1. 保留原管理会话，确认 Tailscale 连通。
2. 将 3x-ui 面板监听地址改为服务器的 Tailscale 地址。
3. 从 Windows 使用 Tailscale 地址测试面板端口。
4. 将私有管理域名解析到 Tailscale 地址，并验证域名证书访问。
5. 通过 Tailscale 完成 SSH 登录。
6. 保持第二个 Tailscale SSH 会话在线后启用 UFW。
7. 再次验证私网 SSH 成功、公网 SSH 失败。
8. 最后验证 3x-ui 面板、订阅上游和公开转换网关各自的链路。

> [!important] 防锁死原则
> 修改面板监听或防火墙前，必须先确认至少一个独立的 Tailscale 管理会话可用；启用防火墙时保留第二会话，并在关闭原会话前从另一客户端重新连接。不能先封公网 SSH 再假设 Tailscale 一定可用。

### 面板

- 面板仅监听服务器的 Tailscale 地址，不再监听公网地址。
- Tailscale 私网访问成功；公网地址访问面板端口失败。
- Web Base Path 已轮换，新路径可登录，旧路径返回 404。
- 2FA 已启用。
- 后续截图再次暴露过管理路径，因此仍需再轮换一次，当前路径不能视为未泄露。

### SSH 与 Tailscale

- Debian、Windows 和 iOS 已加入同一 Tailnet，并曾同时显示在线。
- Windows 已实际通过 Tailscale SSH 登录服务器。
- Windows 到 Tailscale TCP 22 成功，到公网 TCP 22 失败。
- iOS 的 Tailscale 与代理客户端均依赖系统 VPN 能力，实际使用需按管理或代理目的切换。

### 主机防火墙

- UFW 已启用，默认拒绝入站、允许出站。
- 已允许 Tailscale 接口、Tailscale 直连 UDP、Nginx HTTP/HTTPS，以及五个当前节点入站所需端口。
- 未为公网单独放行 SSH、3x-ui 面板和 3x-ui 原生订阅端口。
- 启用 UFW 前保留第二个 Tailscale SSH 会话；启用后会话仍在线，并重新验证了私网 TCP 22。

## 陈旧 13005 入站复盘

### 证据

- 界面只显示五个入站，但当时生成的 Xray 配置额外包含 13005/tcp Trojan，且该端口曾监听但无已建立连接。
- 当前 PostgreSQL 的 inbounds 与 settings 均无 13005，只包含界面中的五个入站。
- 一次可逆的入站备注保存触发热更新后，13005 停止监听。
- 重启 Xray 后，磁盘生成配置也不再包含 13005。

### 结论

当前证据支持“历史生成配置残留”，不支持“恶意创建入站”。这不是全量主机入侵取证结论，后续若出现新的异常监听仍需独立调查。

## 当前订阅架构

公开客户端经 Cloudflare 代理的订阅子域名进入 Nginx，再转发到仅监听回环地址的 tfly-sub-gateway；网关通过 Tailscale 私网读取 3x-ui 原生 Clash 订阅。管理员则通过 Tailscale 访问面板和 SSH。

- sa.tfly.org 用于 Tailscale 私网管理和原生订阅。客户端关闭 Tailscale 后无法访问是预期行为。
- sub.tfly.org 是公开订阅入口。
- Nginx 当前只将 /clash/ 转发到订阅网关，根路径明确返回 404。
- 3x-ui 自定义订阅主题目录当前只有 index.html。它仍需承担复制订阅和唤起客户端的过渡页面，因此暂不清空或删除。
- 公开用户页面尚未通过 Nginx 接入，不能标记为生产就绪。
- 仓库内 Portal 第一阶段仍是本地演示和基础认证实现，尚未完成真实 3x-ui 绑定、生产部署或真实订阅交付。

## 订阅网关 502 故障复盘

### 症状与排查

- 客户端刷新转换订阅时收到 502，网关日志显示上游返回 403，而原生订阅可用。
- 环境文件中的上游协议、主机、端口、路径结构和 token 占位符正常。
- 环境文件路径与 PostgreSQL subClashPath 规范化后匹配。
- 日志中的订阅 ID 前缀仍存在于当前 PostgreSQL 客户端配置。
- 服务器直接请求上游返回 200，但同一时间经本机网关请求仍返回 502。

### 根因与恢复

systemd 的 EnvironmentFile 仅在进程启动时读取。文件修改后，运行中的网关不会自动重读；磁盘配置已经正确，但进程仍使用旧环境值。重启 tfly-sub-gateway 后，真实转换请求由 502 恢复为 HTTP 200。

修改网关环境文件或 Mihomo 模板后，应执行：

    sudo systemctl restart tfly-sub-gateway
    sudo systemctl is-active tfly-sub-gateway
    curl -fsS http://127.0.0.1:18080/healthz

健康检查只证明进程可用。修改上游配置后，还需使用当前有效订阅 ID 做一次不输出凭据的 HTTP 200 冒烟测试。

## Windows 与 Clash/Mihomo 共存

- PowerShell 的 curl 可能是 Invoke-WebRequest 别名；需要 cURL 参数时使用 curl.exe。
- 系统代理或 Clash/Mihomo 可能拦截 Tailscale 私网流量。若 tailscale ping 成功但浏览器打不开面板，应先验证代理绕过。
- curl.exe --noproxy "*" 已验证可绕过系统代理直连 Tailscale。
- Clash/Mihomo 应将 Tailscale CGNAT 网段和私有管理域名置于前部并设为 DIRECT。
- 当前尚无“Clash/Mihomo 与 Tailscale 同时开启后面板再次可用”的最终验收输出，因此此项仍未验证。

## 风险边界

- 本轮降低了面板暴露、SSH 扫描和管理面被直接探测的风险。
- 公开代理入站仍直接使用公网 IP；这些措施不能保证节点 IP 不被网络过滤。
- 停用面板、关闭订阅页、修改域名或仅更换端口，均不能单独解决公网 IP 被封锁。
- 容灾需要独立 IP、不同服务商或地区的备用节点，以及可切换的公开订阅域名。
