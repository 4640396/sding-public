# 2026-07-15 3x-ui 订阅系统阶段总结

> [!summary] 阶段结论
> 当前已形成“3x-ui负责节点与流量、Go网关负责生成完整订阅、Nginx负责HTTPS、3x-ui主题负责临时交付”的可用体系。下一阶段不再把登录能力塞进主题，而是在同一 `3x-ui-sub` 项目中建设独立用户中心。

## 已完成

- 3x-ui面板、节点和订阅功能可用。
- Go订阅网关已部署在回环地址，通过Nginx提供HTTPS入口。
- 网关可读取3x-ui原生节点并注入完整Mihomo模板。
- 输出内容包含节点、策略组、规则、规则集、DNS和嗅探等完整配置。
- 订阅流量、到期时间等响应头得到保留。
- 自定义3x-ui订阅页面可展示流量、有效期、复制地址和客户端导入入口。
- Hysteria2已验证可用；Shadowsocks/Trojan等节点字段可被网关原样保留。

## 客户端与模板结论

### 无需为Clash Verge单独维护模板

网关输出的是标准Mihomo YAML，可供以下客户端共用：

- Clash Party / Mihomo Party；
- Clash Verge Rev（Mihomo内核）；
- 其他支持当前Mihomo语法的客户端。

同一条转换订阅即可。除非确认出现客户端特有的不兼容项，否则不维护第二套模板，避免策略组和规则漂移。客户端侧应关闭会覆盖订阅内容的覆写脚本。

### DIRECT超时不等于直连失效

Windows使用无代理请求Cloudflare 204地址返回 `HTTP 204`，证明本地DIRECT链路正常。客户端界面的手动延迟测试可能使用客户端自己的测试URL和缓存，并不一定使用订阅模板中 `url-test` 的地址。

当前自动选择健康检查使用：

```text
https://cp.cloudflare.com/generate_204
```

如果DIRECT仍在手动测速中显示超时，可将DIRECT从“节点选择”和业务代理组中移除，仅保留在“全球直连”及确实需要直连的规则中；这不会影响直连规则工作。

## 订阅页面与登录边界

3x-ui自定义订阅主题是展示层，不适合实现真正登录：

- Go HTML模板只负责渲染页面；
- 前端JavaScript登录框无法可靠保护订阅数据；
- Clash/Mihomo后台更新订阅时无法使用网页登录Cookie；
- 订阅接口最终仍需要不可猜测的个人token。

因此当前主题不增加登录。订阅ID视为访问凭证，泄露后应重新生成。

## 后续目标架构

```text
浏览器 → Portal用户中心 → 3x-ui管理API
                    ├→ PostgreSQL（账号、套餐、映射、审计）
                    └→ Subscription Gateway → 3x-ui原生订阅

Clash/Mihomo → /clash/<token> → Subscription Gateway
```

职责划分：

- **3x-ui**：节点、入站、客户端、流量和到期时间的运行后端。
- **Portal**：账号登录、套餐展示、流量查询、订阅复制与重置。
- **Gateway**：使用个人token生成完整Mihomo订阅，不依赖浏览器Cookie。
- **PostgreSQL**：保存Portal账号、套餐、3x-ui客户端映射和审计记录。
- **Nginx**：统一TLS入口、路径分流、限速和访问控制。

## 3x-ui API结论

3x-ui已有管理接口，可用于查询或维护客户端、流量、到期时间等信息，因此Portal无需直接修改3x-ui数据库。

安全原则：

- 浏览器不得直接调用3x-ui管理API；
- 由Portal后端在服务器内调用；
- 管理凭据不得下发给前端；
- API只允许回环、内网或明确的服务地址访问；
- PostgreSQL只保存业务账号、套餐和映射，不与3x-ui争抢运行数据的写入权；
- 对重置订阅、变更套餐和停用用户等操作记录审计日志。

## 安全与运维结论

- 面板与订阅服务使用公共可信证书，Cloudflare使用 `Full (strict)`。
- 面板、节点和订阅域名职责分离；不能假设Cloudflare普通橙云可以代理任意TCP/UDP节点端口。
- 网关只监听 `127.0.0.1`，公网仅开放Nginx HTTPS。
- 不在知识库、截图或聊天中保留订阅ID、客户端密码、私钥和管理路径。
- 部署验收后轮换曾公开过的订阅ID。
- 当前1GB内存主机可运行轻量Go网关；Portal开发后需设置资源限制，并持续观察PostgreSQL与3x-ui内存。
