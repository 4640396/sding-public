# 2026-07-31 3x-ui 备用节点数据库恢复续验记录

> [!warning] 当前状态
> 数据库恢复后的管理面已排查到 API 认证层，但主节点尚未使用新 Token 完成测试连接，因此本记录保持 `draft`，不能标记恢复通过。

## 事件摘要

备用节点恢复旧 SQLite 数据库后，3x-ui 同时恢复了旧面板设置和认证状态。直接影响包括：

- 面板端口从标准 `2083` 回退到旧值 `8900`。
- 面板访问地址重新显示公网 IP。
- Web Base Path 仍为原管理路径。
- 面板显示 SSL 已启用，但需要重新核对证书引用。
- 主节点保存的 API Token 与恢复后的副面板数据库不一致。
- 副面板历史入站重新出现在数据库和界面中，部分仍有未到期用户。

## 已取得证据

### 网络与端口

- Windows 能解析备用节点 MagicDNS 名称并通过 Tailscale ping 到节点。
- 私网 TCP 22 可达，证明 Tailscale 与 SSH 管理链路可用。
- 恢复初期 TCP 2083 不可达；备用服务器 `x-ui settings` 显示实际端口为 8900。
- 后续主面板连接测试收到 `HTTP 404 from remote panel`，说明请求已经到达远端 HTTPS 面板和 API 路由前置层。

### 证书

- 原有 Tailscale 证书文件仍存在于受控证书目录。
- 证书 CN 与 SAN 均匹配备用节点 MagicDNS 完整域名。
- 证书由 Let's Encrypt 签发，在本次核验时尚未过期。
- 历史 verified 记录已证明该证书曾被 3x-ui 使用，并通过主节点标准 CA 严格校验。

### API 认证

- 主面板测试连接返回 `HTTP 404 from remote panel`，而非 TCP 或 TLS 错误。
- 3x-ui 官方认证控制器会在普通未登录请求没有匹配的 Bearer Token 时返回 `404`。
- 数据库恢复会恢复副面板的 Token 存储，因此当前最强根因是主面板保留的旧 Token 与副面板恢复后的 Token 不一致。

## 已纠正的操作认知

- 管理脚本 `x-ui settings` 用于展示设置；需要稳定修改时应调用 `/usr/local/x-ui/x-ui` 底层二进制。
- 端口和监听地址使用 `setting` 子命令；证书使用独立 `cert` 子命令。
- 根路径 HTTPS 返回 `404` 可以是正常可达证据；主节点节点测试的 `404` 则需结合 Token 认证判断。
- 证书文件仍在不等于数据库中的证书路径仍正确，恢复后必须重新读取实际设置。

## 旧入站与有效用户处置

- 历史入站不得直接删除，因为仍有未到期用户。
- 关闭旧公网 443 规则只影响实际使用 443 的入站，不影响其他独立高位端口。
- 旧入站需要按仍有效用户逐个恢复监听、UFW 和云安全组规则，或迁移到主节点后再下线。
- 主面板当前版本支持从现有节点导入选定或全部入站；选择全部导入前必须备份数据库并检查与主节点已管理入站的端口冲突。
- 过渡期不再向旧入站新增用户，待到期或用户刷新订阅后逐步关闭。

## 待完成验收

1. 在副面板创建新的主节点专用 API Token。
2. 在主面板节点配置中显式替换旧 Token，测试连接并保存。
3. 确认主面板重新显示副面板版本、Xray 版本、运行时长、客户端数和在线心跳。
4. 核对副面板实际监听地址、2083 端口、Web Base Path 和证书路径。
5. 验证一个主节点远程读操作和一个可逆写操作。
6. 对仍有用户的历史入站核对 UUID 或密码、到期时间、流量、域名、端口和防火墙。
7. 决定采用“全部导入”还是“旧面板过渡管理”，并进行客户端实测。
