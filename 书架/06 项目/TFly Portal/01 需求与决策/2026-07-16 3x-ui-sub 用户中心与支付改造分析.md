# 2026-07-16 3x-ui-sub 用户中心与支付改造分析

> [!warning] 草案状态
> 本文保留为设计分析草案，其中被采纳的选择以 [[2026-07-16 3x-ui-sub 用户中心与支付决策记录]] 为准。目标架构、数据模型和阶段计划不能据此视为已全部实现；当前代码事实以最新源码核验和实施记录为准。

## 1. 结论

当前项目是“订阅转换 Gateway + 3x-ui 展示主题”，没有用户、认证、订单、支付或权益模型。用户中心与支付应作为独立 Portal 业务边界新增，不应继续堆入展示主题，也不建议把完整订单和支付逻辑塞入现有订阅转换 Gateway。

建议保留现有 Gateway 的订阅生成职责，新建 `3x-ui-sub-portal` 负责注册、登录、套餐、订单、支付、权益、3x-ui 客户端映射和审计。Gateway 在输出订阅前增加可撤销的 token 与权益校验。

## 3. 当前架构判断

现有调用链可概括为：

```text
客户端请求 /clash/<token>
  → Gateway 校验 token 格式
  → token 代入 3x-ui 上游 URL
  → 获取原生订阅 YAML
  → 提取 proxies
  → 注入本地 Mihomo 模板
  → 内存缓存并返回
```

该结构适合无状态订阅转换，但缺少用户中心所需的业务事实来源：

- 无用户身份与会话；
- 无套餐、订单和支付记录；
- 无用户与 3x-ui 客户端映射；
- 无订阅 token 哈希、撤销和轮换状态；
- 无权益到期检查；
- 无管理操作和安全审计；
- 无支付回调幂等与开通补偿机制。

## 4. 建议目标架构

```text
浏览器
  → Nginx HTTPS
  → Portal
      ├─ 注册、登录、找回密码、用户中心
      ├─ 套餐、订单、支付、权益、审计
      ├─ PostgreSQL
      ├─ 3x-ui 管理 API 适配器
      └─ 订阅 token 管理

Clash / Mihomo
  → Nginx /clash/<token>
  → Gateway
      ├─ 校验 token 与当前权益
      ├─ 获取 3x-ui 原生订阅
      └─ 生成 Mihomo 配置

支付平台
  → Portal 支付回调入口
  → 验签与幂等处理
  → 订单确认
  → 异步开通或续期 3x-ui 客户端
```

### 职责边界

- **Portal**：账号、认证、套餐、订单、支付、权益、映射和审计。
- **Gateway**：订阅鉴权、上游获取、配置转换和短期缓存。
- **3x-ui**：节点、客户端、流量和到期时间的运行后端。
- **PostgreSQL**：Portal 业务事实，不与 3x-ui 共用业务表。
- **Nginx**：TLS、路径分流、限速和敏感路径日志控制。

Portal 不应让浏览器直接访问 3x-ui 管理 API，也不应直接修改 3x-ui 数据库。具体 API 能力、认证方式和版本兼容性需要在实施前对目标 3x-ui 实例重新验证。

## 5. 用户自助注册与购买流程建议

建议的第一版用户流程：

1. 用户自行注册账号。
2. 完成邮箱验证或其他待确认的账号验证。
3. 登录后选择套餐。
4. Portal 在服务端创建待支付订单并保存价格快照。
5. 用户跳转或扫码完成支付。
6. 支付平台向 Portal 发出异步回调。
7. Portal 验签、校验金额和订单归属，并幂等确认支付。
8. 后台任务创建或更新 3x-ui 客户端。
9. 创建或续期用户权益，生成个人订阅 token。
10. 用户中心展示状态、流量、到期时间和订阅入口。

浏览器返回页显示“支付成功”不能作为开通依据。开通应以服务端验签后的回调或服务端主动查单结果为准。

## 6. 建议数据模型

- `users`：账号、邮箱、密码哈希、状态、角色、验证时间。
- `sessions`：会话摘要、过期时间、撤销状态和登录上下文。
- `plans`：套餐定义。
- `plan_prices`：价格版本、币种和生效区间。
- `orders`：订单号、用户、价格快照、状态和过期时间。
- `payments`：支付渠道、平台交易号、金额和状态。
- `payment_events`：回调事件、验签结果和幂等处理状态。
- `entitlements`：用户获得的流量、有效期和生效状态。
- `xui_instances`：3x-ui 实例元数据和凭据引用。
- `xui_client_bindings`：Portal 用户与 3x-ui 客户端映射。
- `subscription_tokens`：token 哈希、可显示前缀、状态、创建和撤销时间。
- `provisioning_jobs`：支付后的创建、续期、停用和补偿任务。
- `audit_logs`：操作者、动作、目标、结果和必要上下文。

数据库不保存明文订阅 token。明文只在创建或轮换时返回给用户；支付密钥和 3x-ui 管理凭据不写入仓库或普通笔记。

## 7. 订单与开通状态建议

```text
pending → paid → provisioning → active
       ↘ expired
       ↘ cancelled

paid / active → refund_pending → refunded
```

需要通过数据库唯一约束和事务防止重复回调造成重复开通。建议至少对“支付渠道 + 平台交易号”和“支付事件 ID”建立唯一约束。

支付状态与开通状态应分离：支付成功但 3x-ui 暂时不可用时，订单仍可保持已支付，开通任务进入重试或人工处理，不能把支付回调线程与外部开通操作强耦合。

## 8. 安全约束

- 密码使用适合密码存储的哈希算法，并保存算法参数以便升级。
- 会话 Cookie 使用 `HttpOnly`、`Secure` 和合适的 `SameSite` 策略。
- 注册、登录、找回密码、支付创建、回调和订阅下载分别限速。
- 用户查询必须从服务端会话确定用户身份，不接受浏览器提交任意用户 ID。
- 支付金额、套餐和订单归属必须由服务端重新加载，不能信任前端字段。
- 支付回调必须验签、校验时间窗口并处理重复事件。
- 订阅 token 应高熵随机生成，数据库仅存哈希，并支持撤销和轮换。
- Nginx 和应用日志不得记录完整订阅 token、密码、支付密钥或 3x-ui 管理凭据。
- 管理操作、token 重置、退款和人工补单需要审计与二次确认。
- 3x-ui API 故障时展示“数据暂不可用”，不能把未知流量误报为零。

## 9. 对现有代码的影响范围

| 范围 | 影响 | 草案建议 |
|---|---|---|
| Gateway 路由 | 高 | `/clash/<token>` 输出前校验 token 与权益 |
| Gateway 缓存 | 高 | 支持撤销失效，缓存有效期不得越过权益截止时间 |
| Portal | 新增 | 独立 Go 应用，承担 Web 页面与业务 API |
| PostgreSQL | 新增/高 | 用户、会话、订单、支付、权益、任务、审计 |
| 3x-ui 集成 | 高 | 创建、续期、禁用、流量同步及失败补偿 |
| Nginx | 中 | 增加 Portal、回调与内部接口路径及限速 |
| 现有主题 | 低 | 迁移期保留，Portal 稳定后再决定退役 |
| 测试 | 高 | 增加越权、幂等、补偿、撤销和并发测试 |
| 部署资源 | 中高 | Portal 与 PostgreSQL 需要独立容量评估 |
| 运维 | 高 | 数据迁移、备份恢复、对账、告警和密钥轮换 |

### Gateway 缓存风险

当前缓存以明文 token 为键并按固定 TTL 返回结果。引入禁用、退款、到期和 token 轮换后，如果没有显式失效或权益截止约束，旧订阅可能在撤销后继续命中缓存。实施时需要选择以下机制之一或组合使用：

- Gateway 每次缓存未命中时向 Portal 校验，缓存到期不超过权益截止时间；
- Portal 在禁用、退款或轮换时调用 Gateway 内部失效接口；
- 使用共享的短期撤销版本号或事件通知；
- 对高风险动作缩短缓存或完全跳过缓存。

## 10. 分阶段方案

### 阶段一：用户中心基础

- 新建 Portal 骨架和数据库迁移机制。
- 完成自行注册、账号验证、登录、退出和找回密码。
- 完成用户、会话和审计模型。
- 只读展示 3x-ui 流量与到期时间。
- 保留现有主题和订阅入口。

### 阶段二：套餐、订单和模拟支付

- 建立套餐、价格、订单、支付事件和权益模型。
- 使用内部模拟支付适配器验证订单状态机。
- 完成幂等开通任务、失败重试和人工补单入口。
- 管理端可查看订单、支付和开通状态。

### 阶段三：真实支付渠道

- 定义支付渠道抽象。
- 接入选定渠道的创建支付、验签、回调、查单和退款。
- 增加支付回调重放防护、对账和异常告警。
- 支付凭据只保存在服务端受控环境。

### 阶段四：订阅接管

- Portal 生成高熵订阅 token，数据库仅保存哈希。
- Gateway 增加 token 和权益校验。
- 支持 token 重置、禁用、过期和缓存失效。
- 新用户只通过 Portal 获取订阅。

### 阶段五：迁移收口

- 迁移旧用户与 3x-ui 客户端绑定关系。
- 逐步停止直接交付 3x-ui 订阅主题。
- 限制 3x-ui 原生订阅入口只供 Gateway 使用。
- 完成备份恢复、支付对账和故障演练。

## 11. 第一版范围建议

以下是建议而非已确认需求：

- 公开注册，但要求账号验证；
- 单账号仅有一个当前有效套餐；
- 支持一次性购买与续费；
- 暂不实现钱包余额、充值账户、优惠码和自动续费；
- 支付成功后异步开通，失败可重试和人工补偿；
- 现有主题在迁移期继续保留。

所有未确认项集中记录在 [[2026-07-16 3x-ui-sub 用户中心与支付待决策清单]]。

## 12. 验收方向

- 用户只能访问自己的账号、订单、流量和订阅。
- 重复支付回调不会重复开通或重复续期。
- 支付金额和订单套餐由服务端确认。
- 支付成功但外部开通失败时可追踪、重试和补偿。
- token 重置、用户禁用、套餐过期或退款后，旧订阅按确定策略失效。
- 3x-ui API 故障不会导致越权、数据串户或错误清零。
- 管理操作、退款、补单和 token 重置可审计。
- Portal 与 Gateway 的资源限制经过目标服务器实测。
