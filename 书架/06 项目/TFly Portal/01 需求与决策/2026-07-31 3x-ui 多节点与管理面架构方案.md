# 2026-07-31 3x-ui 多节点与管理面架构方案

> [!warning] 状态边界
> 本文仍是整体架构方案，当前状态为 draft。单个备用节点、私网管理链路和一个测试入站已经实施并验收，但订阅聚合、失联行为、生命周期操作、证书自动续期和故障切换尚未完成；已验证证据见 [[2026-07-31 3x-ui 备用节点与官方多节点接入验收记录]]。

## 目标

- 管理面不暴露公网：3x-ui 面板、SSH、数据库和节点管理通信只走 Tailscale。
- 数据面保持可用：用户节点入站按协议需要使用各节点公网地址。
- 一个节点或公网 IP 故障时，不影响全部用户。
- 用户继续使用稳定的公开订阅域名，不因后端节点迁移而频繁更换订阅地址。
- 订阅转换、节点运行和未来 Portal 分属清晰边界。

## 非目标

- 不承诺任何公网 IP 永不被过滤。
- 不把修改域名、端口、面板路径或关闭订阅页视为 IP 容灾。
- 不把同一服务器上的多个入站称为多节点容灾；它们共享同一公网 IP 和主机故障域。
- 不把 Cloudflare 免费橙云用于其不支持的任意 RAW TCP 或 UDP 节点流量。

## 推荐的逻辑分层

### 管理面

- 管理员设备、中心 3x-ui 和所有节点主机加入同一 Tailnet。
- 面板、SSH、数据库和节点控制接口只监听 Tailscale 或回环地址。
- 使用 Tailscale ACL 或 grants 将管理员、中心服务和节点角色分开，避免 Tailnet 内默认全互通长期存在。
- 关闭公网 SSH 与公网面板端口；紧急恢复依赖云服务商控制台或救援模式。

### 订阅与交付面

- 公开订阅域名继续由 Cloudflare 代理到 Nginx。
- Nginx 只开放明确的用户页面和订阅路径。
- tfly-sub-gateway 继续仅监听回环地址。
- 网关经 Tailscale 读取 3x-ui 原生订阅，不直接依赖公网管理端口。
- 用户只保存公开转换订阅地址；节点迁移和替换由订阅内容消化。

### 节点数据面

- 每台节点主机使用独立公网 IP，优先分散到不同故障域；同一 IP 上增加多个协议只能提供协议选择，不能提供 IP 容灾。
- 节点域名与管理域名分离。直连节点使用仅 DNS 解析；只有明确兼容 Cloudflare HTTP 代理的传输才考虑橙云。
- 每台节点只开放其实际启用的入站端口和 Tailscale 所需流量。
- 节点证书、客户端凭据和订阅 ID 分开管理；避免所有节点共用一组可横向扩散的高权限凭据。

## 3x-ui 多节点实施选项

### 选项 A：中心 3x-ui 管理远程节点

目标形态：

- 一台中心主机承载 3x-ui、PostgreSQL、订阅网关和 Nginx。
- 多台远程节点只承载节点运行组件。
- 中心与远程节点之间的管理通信走 Tailscale。
- 用户订阅由中心统一生成。

优点：

- 单一管理入口，用户、流量和订阅集中管理。
- 节点公网无需暴露面板与 SSH。
- 更换单个节点时公开订阅域名不变。

限制与待核验：

- 必须核验 3x-ui 3.6.0 官方多节点功能、节点注册方式、认证材料、配置下发、流量回传、失联行为和版本兼容性。
- 必须确认节点通信能绑定或路由到 Tailscale，而不要求开放额外公网管理端口。
- 中心主机仍是控制面和订阅面的单点，需要备份与恢复方案。

当前推荐：在官方能力核验通过后优先采用。

### 选项 B：每个节点独立运行 3x-ui

目标形态：

- 每个节点独立运行自己的 3x-ui 和运行数据。
- 管理员通过 Tailscale 分别登录。
- 由独立聚合层生成跨实例订阅。

优点：

- 单节点故障和配置错误的隔离更强。
- 不依赖中心 3x-ui 的远程节点功能。

代价：

- 用户、流量、到期时间和凭据需要跨实例同步或人工维护。
- 当前 tfly-sub-gateway 只接受一个上游模板，不具备多实例聚合与去重能力。
- 当前 Portal 也未完成跨实例绑定。

当前判断：作为中心多节点能力不满足要求时的备选，不直接实施。

### 选项 C：单机多入站

当前主机已有多个协议入站，但它们共享同一公网 IP、主机、网络和防火墙。

当前判断：可用于协议兼容和客户端选择，不属于多节点或 IP 容灾方案。

## 推荐拓扑

    管理员设备
      → Tailscale
      → 中心 3x-ui / SSH / PostgreSQL
      → Tailscale
      → 节点 A、节点 B、节点 C

    用户客户端
      → 公开订阅域名
      → Cloudflare
      → Nginx
      → tfly-sub-gateway
      → Tailscale
      → 3x-ui 原生订阅

    用户实际代理流量
      → 节点 A、节点 B、节点 C 的独立公网入站

管理流量、订阅交付流量和用户代理流量必须分别评估，不应因为都属于同一系统而共用相同暴露策略。

## 分阶段实施

### 阶段 0：当前安全基线

- [x] 中心面板只走 Tailscale。
- [x] SSH 只走 Tailscale。
- [x] UFW 默认拒绝入站。
- [x] 公开订阅入口与私有原生订阅分离。
- [x] PostgreSQL、证书和 Xray 配置建立备份。

### 阶段 1：正式核验

- [x] 阅读目标 3x-ui 3.6.0 官方多节点架构资料，并结合实机界面核验。
- [x] 在当前界面确认节点管理功能和必填字段。
- [x] 确认控制通信由主节点经 HTTPS 调用子节点 API，使用专用 Token 和标准 CA 校验。
- [x] 确认管理通信可以完全通过 Tailscale 地址和 MagicDNS 证书完成。
- [ ] 确认节点离线、中心重启和版本不一致时的行为。

### 阶段 2：单个测试节点

- [x] 准备一台与现网不同公网 IP 的测试节点。
- [x] 先加入 Tailnet并验证私网 SSH。
- [x] 按最小端口原则配置防火墙。
- [x] 新建一个低影响 VLESS + REALITY + Vision 测试入站。
- [ ] 验证下发、启动、流量统计、订阅生成、禁用和删除。
- [ ] 验证中心或 Tailscale 短暂中断时，节点现有转发是否继续。

### 阶段 3：订阅与故障切换

- [ ] 让公开转换订阅同时包含中心节点与测试节点。
- [ ] 验证客户端能刷新并看到多节点。
- [ ] 停止单个测试节点，确认其他节点继续可用。
- [ ] 替换测试节点 IP 后，确认用户无需更换公开订阅地址。
- [ ] 验证流量、到期时间和用户隔离不串户。

### 阶段 4：生产扩展

- [ ] 至少使用两个独立公网 IP，并尽量分散服务商或地区故障域。
- [ ] 制定节点命名、标签、证书、监控和轮换规范。
- [ ] 为中心控制面和订阅面建立恢复时间目标与恢复步骤。
- [ ] 再评估是否需要第二订阅网关或中心主机冷备。

## 验收标准

- 公网无法访问任何节点的管理面和 SSH。
- 管理员通过 Tailscale 可管理所有节点。
- 公共订阅地址在客户端关闭 Tailscale 后仍可刷新。
- 公开订阅包含至少两个不同公网 IP 的节点。
- 停止任一节点后，其他节点和订阅服务仍可用。
- 中心重启后节点行为符合实施前确认的官方语义。
- 防火墙实际规则与文档、云安全组一致。
- 日志、截图和知识记录不包含完整订阅 ID、管理路径或私钥。

## 需要用户决策

- 首个测试节点放在哪个服务商与地区。
- 是否接受中心 3x-ui 作为控制面单点，还是要求控制面也具备冷备。
- 节点按用户共享、按线路共享，还是按用户隔离。
- 预算允许的独立公网 IP 数量。
- 故障切换是依靠客户端策略组自动选择，还是由管理员更新订阅后切换。
