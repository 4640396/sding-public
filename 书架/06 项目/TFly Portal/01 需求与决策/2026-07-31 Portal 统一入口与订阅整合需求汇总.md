# 2026-07-31 Portal 统一入口与订阅整合需求汇总

> [!important] 当前状态
> 本文是供次日继续决策的需求汇总，状态为 draft，不代表已授权实施。今天不创建新前端、不修改生产服务，也不改变现有订阅地址。

## 一、问题定义

当前公开订阅依赖包含订阅 ID 的完整地址。用户不知道自己的地址时，管理员必须逐个复制和发送，带来以下问题：

- 新用户开通依赖人工交付。
- 订阅地址更新或轮换后需要再次人工通知。
- 用户难以自行查看流量、到期时间和客户端导入方式。
- 完整订阅地址容易在聊天、截图和转发中泄露。
- 多节点和后端迁移后，用户入口缺少稳定抽象。

因此，仅提供公开的订阅转换 URL 不能构成完整用户产品。用户首先需要一个账号入口，登录后由系统自动识别其绑定关系并展示订阅。

## 二、目标产品边界

Portal 是唯一面向普通用户的产品入口；订阅只是 Portal 的一个功能模块，不是需要用户理解的独立系统。

用户只需要知道：

- Portal 公开地址；
- 自己的账号与密码。

用户不需要知道：

- 3x-ui 面板域名、端口或随机管理路径；
- 3x-ui 管理员账号或 API Token；
- 3x-ui 原生订阅地址；
- 自己在 3x-ui 中的客户端标识；
- Gateway 的内部地址和上游配置。

## 三、目标用户流程

### 首次使用

1. 用户进入 Portal。
2. 注册并完成邮箱验证，或使用管理员预创建的账号。
3. Portal 根据数据库中的绑定关系找到该用户对应的 3x-ui 客户端。
4. 用户首页自动展示服务状态、流量、到期时间和“我的订阅”。
5. 用户可以复制订阅、显示二维码或一键唤起支持的客户端。

### 日常使用

1. 用户登录 Portal 查看自己的状态。
2. 用户无需再次向管理员索要订阅地址。
3. Clash/Mihomo 等客户端可脱离 Portal 登录会话，凭独立订阅 Token 刷新配置。
4. 用户主动重置 Token 后，旧地址按既有 accepted 决策立即失效。

### 管理员流程

第一阶段可以由管理员完成 Portal 用户与 3x-ui 客户端绑定；绑定完成后不再手工发送完整订阅地址。后续自动开通阶段再由订单或套餐流程创建 3x-ui 客户端并自动建立绑定。

## 四、统一域名与路由草案

建议同一个公开域名同时承载 Portal 页面和订阅接口：

    /                       Portal 首页或登录后概览
    /login                  用户登录
    /register               邮箱注册
    /account                账号设置
    /subscription           我的订阅页面
    /api/me                 当前用户信息
    /api/me/subscription    当前用户订阅元数据
    /api/me/token/reset     重置当前用户订阅 Token
    /clash/{portalToken}    Clash/Mihomo 订阅
    /sub/{portalToken}      通用订阅
    /app/{portalToken}      复制、二维码与客户端唤起页面

页面路由使用 Portal 会话鉴权；机器订阅路由使用独立 Token，不依赖登录 Cookie。

## 五、认证边界

### 普通用户认证

普通用户必须使用 Portal 自己的账号、密码、会话和角色体系。现有 Go Portal 已实现以下基础：

- 邮箱注册与验证；
- Argon2id 密码哈希；
- 登录与退出；
- HttpOnly 会话；
- CSRF 防护；
- 登录失败限速与短时锁定；
- 找回密码与会话撤销；
- PostgreSQL 用户、会话、绑定和审计基础表。

### 不能复用 3x-ui 管理登录

本次对目标 3x-ui 3.6.0 API 文档的只读核验确认：

- POST /login 创建的是面板会话 Cookie。
- 面板 API 接受管理员会话或 Bearer API Token。
- API Token 被明确描述为完整管理员凭据。
- 客户端 API 同时包含读取、创建、更新、删除、重置流量等管理能力。

因此普通用户浏览器不得直接调用 3x-ui 登录或管理 API，也不得获得管理员 Cookie、API Token、用户名或密码。

Portal 后端可通过 Tailscale 私网调用 3x-ui，但必须执行用户绑定校验、接口白名单、超时、审计和错误隔离。

## 六、订阅 Token 模型

长期目标是不直接向用户暴露 3x-ui 原生 subId，而是由 Portal 生成自己的不透明订阅 Token：

    Portal Token
      → 查询 Token 哈希与状态
      → 找到 Portal 用户
      → 检查账号、套餐和到期状态
      → 找到 3x-ui 客户端绑定
      → 服务端读取原生订阅
      → 转换并返回目标格式

要求：

- 数据库只保存 Token 哈希和必要的可展示前缀。
- 明文 Token 只在创建或轮换时返回。
- Token 与用户、权益和绑定关系关联。
- 禁用、到期、退款或用户主动重置时可立即撤销。
- Nginx 和应用日志不得记录完整 Token。
- 订阅内容缓存与 Token 鉴权结果分离。
- 后端节点或 3x-ui subId 变化时，优先保持用户的 Portal 订阅地址稳定。

## 七、Portal 与订阅转换的代码边界

### 产品边界

产品上只有一个 Portal。用户不应感知 Gateway 是独立服务。

### 过渡实施

为避免影响现有订阅，第一阶段可以保留 tfly-sub-gateway 独立进程：

- Portal 负责账号、绑定、权限和订阅展示。
- Gateway 继续负责 YAML 转换。
- Portal 页面生成公开订阅入口。
- 对用户而言仍是同一域名和同一产品。

### 最终方向

在 Token 鉴权与绑定模型稳定后，将 Gateway 的转换逻辑移动到 Portal 内部 subscription 模块，最终由一个 Go 服务提供：

- 用户页面；
- 用户 API；
- 管理员路由；
- Token 鉴权；
- 原生订阅读取；
- Mihomo 配置转换。

这会减少 systemd 服务、环境文件和跨进程配置同步，也可避免修改环境文件后忘记重启 Gateway 的故障。

## 八、前端技术方向

3x-ui 当前官方前端采用 React、TypeScript、Vite、Ant Design、TanStack Query 和 Zod，并将构建产物嵌入 Go 二进制。

本项目的候选方向：

### 方案 A：继续 Go 服务端渲染

- 复用当前 Portal。
- 实施快、依赖少、资源占用低。
- 适合先完成登录、绑定、订阅和流量展示。

### 方案 B：在现有 Portal 内增加 React 前端

- 在 3x-ui-sub-portal 内增加 frontend 目录，而不是新建第二套独立产品。
- Go 继续承担认证、会话、权限、数据库、3x-ui 适配和订阅转换。
- React 只调用 Portal 自己的 API，不调用 3x-ui 管理 API。
- 适合后续套餐、订单、多节点、管理端和复杂交互。

### 当前建议

不另建独立 React 产品。若明天确认需要 React，则把它作为现有 Portal 的前端层，并参考 3x-ui 官方技术栈；是否在下一阶段立即引入 React 尚未决定。

## 九、与既有决策的关系

继续沿用 2026-07-16 accepted 决策中的以下内容：

- 允许公开邮箱注册并强制邮箱验证。
- 第一版一个账号绑定一个 3x-ui 客户端和一个 3x-ui 实例。
- 浏览器不直接访问 3x-ui 管理 API。
- Portal 使用独立 PostgreSQL 数据库和角色。
- 用户重置订阅 Token 后旧 Token 立即失效。
- 管理端和用户端使用同一 Portal 程序、不同路由。

存在一项待重新决策的冲突：

- 旧 accepted 决策：Portal 与 Gateway 同仓库但作为独立进程运行。
- 今日新方向：订阅是 Portal 内部功能，最终可并入同一 Go 程序。

在用户明天明确选择前，旧 accepted 决策仍是正式基线，今日合并方向仅为 draft。

## 十、当前实现状态

### 已有

- Go Portal 的基础账号、认证、会话、找回密码和数据库模型。
- 3x-ui 只读适配器雏形。
- Go 订阅转换 Gateway。
- 自定义订阅主题。
- 公开 /clash/ 转换入口。
- Tailscale 私有管理面。

### 尚未完成

- Portal 生产部署。
- Portal 与真实 3x-ui 用户绑定。
- 登录后自动展示当前用户订阅。
- Portal Token 与订阅鉴权。
- React 前端。
- 管理员绑定界面。
- 订阅 Token 重置闭环。
- Gateway 并入 Portal。
- 真实 SMTP、支付和自动开通。

## 十一、建议实施阶段

### 阶段一：用户能自行取得订阅

- 完成 Portal 与真实 3x-ui 的只读连接。
- 实现管理员绑定 Portal 用户与 3x-ui 客户端。
- 登录后展示流量、到期时间和当前订阅。
- 先复用现有 Gateway，避免改变生产订阅。

### 阶段二：Portal Token

- 增加 Token 数据模型和迁移。
- 实现创建、鉴权、撤销、轮换和限速。
- Gateway 请求改为通过 Portal 绑定关系读取上游。
- 验证用户只能读取自己的订阅。

### 阶段三：统一程序

- 将 YAML 转换逻辑移动到 Portal subscription 模块。
- 迁移现有订阅请求。
- 并行观察后停用独立 Gateway。

### 阶段四：完整用户中心

- 根据已确认方向引入或扩展 React 前端。
- 增加套餐、订单、多节点选择、通知和管理端。
- 支付只在取得官方接口和单独生产授权后实施。

## 十二、验收边界

- 用户只凭 Portal 账号即可找到自己的订阅。
- 管理员不再通过聊天手工发送或更新订阅地址。
- 普通用户只能读取自己的状态、流量和订阅。
- 浏览器无法获得 3x-ui 管理凭据。
- 客户端关闭 Tailscale 后仍可刷新公开订阅。
- 订阅 Token 可撤销和轮换，旧 Token 按 accepted 决策立即失效。
- 单个后端节点替换后，用户公开 Portal 订阅地址尽量保持稳定。
- 3x-ui 或订阅上游故障时显示明确错误，不误报流量为零，不泄露内部信息。
