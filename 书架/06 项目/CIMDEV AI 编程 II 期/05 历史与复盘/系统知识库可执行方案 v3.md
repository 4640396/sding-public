# 系统知识库可执行方案 v3

> [!note] 历史快照说明
> 本文根据升级第四版前的第三版现行文件整理，保留其关键职责、架构和实施顺序。第三版已被当前第四版替代，不作为现行技术实施依据。

## 1. 第三版核心判断

第三版认为 cx-aicode 已经包含需求分析、方案设计、代码生成、Code Review 和测试完整操作，并将其视为 AI 编程流程主控；Workspace作为正式知识服务，通过知识适配层在各阶段提供上下文。

第三版进一步收缩首期范围：先用一个系统、一个知识库、一个通用问答APP和cx-aicode一个既有阶段验证价值；验证后扩展阶段，最后才建设知识维护Agent。

## 2. 第三版在线架构

```text
开发者
→ cx-aicode既有工作流
→ cx-aicode Python后端知识适配层
→ Workspace问答APP或检索接口
→ KnowledgeContext
→ cx-aicode既有模型调用
```

第三版提出在Python后端实现统一接口：

```python
get_system_knowledge(
    system_id,
    stage,
    query,
    module=None,
    applicable_version=None,
    top_k=None,
)
```

它已取消将完整仓库、分支、文件、源码和会话作为统一必传载荷，并建议通过项目知识绑定确定系统和知识库。

## 3. 第三版阶段使用策略

|阶段|主要知识|
|---|---|
|需求分析|背景、术语、业务边界、流程和状态机|
|方案设计|架构、模块边界、API、数据库和技术债务|
|代码生成|编码规范、典型代码、接口和数据规则|
|Code Review|Review规则、安全、历史错误和系统特例|
|测试|业务规则、状态机、验收条件和历史缺陷|

推荐少量基础预取与执行中定向查询结合，知识失败时保留原流程并显示降级状态。

## 4. 第三版实施顺序

1. 选择一个试点系统和验证样本。
2. 单独验证Workspace知识问答。
3. 在cx-aicode Python后端实现最小 `WorkspaceKnowledgeClient`。
4. 在一个既有阶段增加知识调用并开展有无知识对照。
5. 扩展需求分析和测试。
6. 扩展设计和代码生成，并产品化绑定、缓存、日志和降级。
7. 建设知识维护Agent。
8. 三系统试点后推广至16个系统。

## 5. 第三版保留价值

- 首期验证范围较小，不一次建设16个系统。
- 明确Workspace不会接管AI编程流程。
- 在线知识消费与离线知识维护分开。
- 采用有无知识对照验证实际价值。
- 知识维护Agent延后到消费价值成立后。
- 强调来源、版本、拒答、权限、降级和过期知识退出检索。

## 6. 被第四版替代的关键假设

用户随后明确：cx-aicode主要是一个Skill和一组Markdown约束文件；真正执行需求、设计、编码、Review和测试的是加载Skill的Agent。cx-aicode虽然有Python后台，但该后台主要用于记录，并非流程编排和模型上下文服务。

因此第三版以下假设不再适用：

- 把cx-aicode本身描述为运行时流程主控；
- 默认由cx-aicode Python后台实现Workspace知识客户端；
- 在Python后端五个工作流模块增加知识Hook；
- 由后台组装知识与模型上下文；
- 默认由后台维护项目知识绑定、Token和Workspace调用。

第四版将在线链路调整为：cx-aicode Skill规定何时查询，Agent实际调用Workspace知识工具，Python后台仅按需记录知识使用情况。详见 [[../01 需求与决策/CIMDEV AI 编程 II 期系统知识库可执行方案]] 和 [[方案版本演进记录]]。
